`desktop/gnome/` builds `tokkl-timerd`, a headless Qt service that runs the shared `tokklcore` (`desktop/core`) and adds no timer rule of its own. The running entry, the pause chain and the Pomodoro session are the server's, read through one `TimerStateClient`, so a change on any device shows in either mode; the service stores only the Pomodoro mode and the sound choices. It owns `org.tokkl.Timer1` at `/org/tokkl/Timer1` on the session bus. A GNOME panel extension or any other client drives it over D-Bus. Requests carry the client name `tokkl-gnome`.

`desktop/gnome/src/main.cpp` is the daemon's composition root: it builds the settings file, clock, connection, `TimerController` and its `TimerStateClient`, Pomodoro store, sound choices, preferences client, session (on the timer's coordinator), `ServiceSettings` and `ConfigurationAdapter`, and hands `TimerService` its `Parts`. `TimerService` builds nothing; it reads the timer's `TimerModel`, acts through its `TimerCoordinator`, and maps properties and methods onto the bus. `ConfigurationAdapter` (`desktop/gnome/src/configurationadapter.h`) owns `Configure`: it calls `ServiceSettings::configure` and sends the delayed reply or error once the credential store has answered. `autotests/timerservicetest.cpp` builds the same graph in its `Daemon` struct, in the same order as `main.cpp`; change both together.

The interface description is `desktop/gnome/dbus/org.tokkl.Timer1.xml`. It lives in `dbus/` because the root `.gitignore` ignores `data/`. Contract rules:

- Properties are `Running`, `StartTime`, `LocalStartTime`, `Paused`, `ChainSeconds`, `IndicatorState`, `IndicatorColor`, `Projects`, `ProjectsIncomplete`, `ChosenProject`, `ChosenProjectName`, `Billable`, `Status` and `ErrorString`, the Pomodoro ones, among them `SessionActive`, `CanStartSession` and `PomodoroLengthLimits`, `Actions`, `Presentation`, `AlarmError` and `InterfaceVersion`. Methods are `Start`, `Stop`, `Pause`, `Resume`, their request forms `RequestStart`, `RequestStop`, `RequestPause` and `RequestResume`, `SetProject`, `SetBillable` and `Configure`; the one signal of the interface is `RequestFinished`. Add members only; existing clients read the old ones.
- `InterfaceVersion` (`u`) is the version of the contract the service implements, `TimerService::version`. Version 1 is the first to publish it and publishes every member described, `Actions`, `Presentation` and `PomodoroLengthLimits` among them. Raise it by one in a release that adds members. The extension picks its fallbacks by it: `publishes()` in `timer1.js` (Node-tested) and `publishedProperty()` in `timer1proxy.js` take the property when the version says the service publishes it, and judge a service without `InterfaceVersion` by whether the property is there. `legacyactions.js`, `legacylimits.js` and `legacyPresentation()` in `menumodel.js` state in their headers that their older-service paths go once every supported `tokkl-timerd` publishes `InterfaceVersion`; the no-service menu and words stay.
- `StartTime` is the server's start in Unix seconds, 0 when stopped or paused; it keeps that meaning for older clients. `LocalStartTime` is the same start on this machine's clock, the server's start minus `TimerStateClient::serverOffsetMs()`, so on a machine whose clock differs from the server's the extension shows the elapsed time the KDE and macOS apps show. `ChainSeconds` is what the server stored for the entries the chain's pauses stopped, 0 without a chain, so elapsed time is `ChainSeconds` plus the clock minus `LocalStartTime` while running, and `ChainSeconds` alone while paused. The extension falls back to `StartTime` when a service from before `LocalStartTime` lacks it. While `Paused` is true, `Running` is false. `Pause` stops the running entry and keeps the chain; `Resume` starts its clone; `Stop` ends the chain and, while paused, asks the server to discard it, which needs a connection (see `practice-kde-timer-controller-rules`). `Running` stays false during a session, whose open pomodoro is not a timer; `Start`, `Stop`, `Pause` and `Resume` return false while a session is active. `CanStartSession` is true when Pomodoro mode is on, no session action waits, and `TimerModel::canStartNew()` holds: the timer can write (no 429 cooldown, workspace not lost, no write or settling in flight, a state read), nothing runs and no session is active. `StartSession` is allowed only then. Do not enable the extension's Start session item from other properties.
- `Actions` (`a{sa{sv}}`) is the core's `MenuActionStates` with `MenuActionPolicy::gnome()`: for run, startSession, nextPhase, endSession, project, billable and mode it gives visible, enabled (false whenever visible is) and the label key ("start" or "stop", the upcoming phase, "projectRunning" or "projectPaused" while locked, "pomodoroModeLocked"). The extension renders its menu from it. Without it, from no service or one from before `Actions`, the extension falls back to the rules it had before (`extension/legacyactions.js`), as an extension updated from extensions.gnome.org often meets an older packaged service. The other properties stay for older clients.
- The interface description is the one source of the contract. `scripts/pack-extension.sh` copies it into the extension zip, `timer1proxy.js` reads it next to itself (`TIMER1_XML_FILE` in `timer1.js`) and builds the proxy from it, and `ci/shell-test.sh` packs it the same way. `ChosenProject` 0 means no project. `ChosenProjectName` is the name of the project the core resolved for the running entry, archived projects included; while stopped it comes from `Projects`. `Projects` alone cannot name an archived running project, so clients read `ChosenProjectName` for the label. It is declared in `dbus/org.tokkl.Timer1.xml`. `Projects` and `ProjectsIncomplete` come from the core's `ProjectChoices`; `ProjectsIncomplete` is true when the workspace has more active projects than the paging limit let the service read, and the extension's project menu then shows the note the KDE and macOS menus show.
- `PropertiesChanged` lists only the properties whose value changed since the last signal, never the whole set, and the service sends at most one per turn of the event loop. Every `Q_PROPERTY` of `TimerService` is published (`TimerService::publication()`), read through its getter. The constructor lists the core signals once with `watch()`: the model's, the session's, the preferences', the sounds', the alarm's (in `setAlarm()`) and the state client's `offsetChanged`, which `followStateClient()` reconnects when the model's client changes, because `LocalStartTime` reads the offset. Any of them has every property read again on the next turn, and the diff against what the bus last saw sends only what changed. There is no table of which signal changes which property, so a getter cannot fall out of step with one. The whole set is read only on a core signal, never per tick (elapsed time and the countdown are not watched). A new property is a `Q_PROPERTY` and its getter, plus a watched signal when the getter reads something no watched signal announces. A method sends what it changed before it answers, so a client's cached properties are current when the reply arrives. `changesArriveOncePerTurn` checks that one state change sends one signal with every changed value.
- `Presentation` (`a{sv}`) is the core's `StatusPresentation` with `StatusPolicy::gnome()`: `summary` and `menuLine` (`as`, part keys such as "activity", "session", "project", "connection", "detail", "pomodoroMode") and `mark` ("none", "pending", "alert", "unconfigured"). The extension's `describeTime()` renders its parts. Without it, from an older service, `legacyPresentation()` in `menumodel.js` decides the parts by the same rules; `tests/statuspresentation.test.js` checks it against every case of `desktop/core/autotests/statuspresentation.json`, which the core test reads too.
- `AlarmError` (`s`) is `PomodoroAlarm::failure()`: why the last ring or `PreviewSound` was silent, empty when it played. The extension shows it as the menu's message when no failed call or session message outranks it.
- `RequestStart`, `RequestStop`, `RequestPause` and `RequestResume` do what the plain method does and return a request id, 0 when nothing was sent. `RequestFinished(t request, b ok, s error)` follows the server's answer, after the properties it changed: `error` is `TimerCoordinator::writeFinished()`'s message, as `ErrorString` words it, and empty when a new generation ended the write. The service follows one request at a time, as the timer sends one write at a time. The plain methods keep their signatures and send no `RequestFinished`.
- `PomodoroLengthLimits` (`a{sa{si}}`) is `PomodoroPreferences::limits()` keyed as `PomodoroLengths`, each with min, max and default. The extension's preferences build their ranges from it and fall back to `legacylimits.js` without it.
- `Configure` with an empty secret keeps the secret the credential store holds for that account. A nonempty one is saved first; if the store refuses, the call fails with `org.tokkl.Timer1.Error.CredentialStore` (`ConfigurationAdapter::credentialStoreError`) and the settings stay as they were. A call that a later `Configure` replaced while the store saved its secret fails with `org.tokkl.Timer1.Error.Superseded` (`ConfigurationAdapter::supersededError`, `ServiceSettings::Outcome::Kind::Superseded`): its settings were never applied, and the preferences keep settings only on success. A service from before that error answered such a call with success.
- `Activate` returns "ignored" whenever nothing applied, also in Timer mode when the timer's toggle sent nothing (no account, no state read, a write waiting). The extension acts only on "open-menu".
- Secrets live in QtKeychain: libsecret (GNOME Keyring) on GNOME, KWallet if the desktop is KDE.
