`Tokkl::TimerController` (`desktop/core/src/timercontroller.h`, QML type `TokklTimer`) is the timer as one object, in two halves. `TimerModel` (`timermodel.h`), which the controller is, holds what a panel shows: the view of the accepted state, elapsed time, the projects (`ProjectCatalog`, `ChosenProject`), the next-start choice (`NextStartSelection`), the status and canWrite, with read-only accessors and every view signal. `TimerCoordinator` (`timercoordinator.h`), which the controller owns, holds the actions and what keeps them safe: the state client and connection it binds, the epoch, the `MutationGate` and its messages, and the lost-workspace block and rediscovery. It reports the end of each write in `writeFinished(ok, message)`, with the words `errorString()` shows; a new generation ends a write still on its way with an empty message. The model owns the project catalog and the next-start selection and applies the next-start defaults (the stop reply from `entryEnded()`, `NextStartSelection::stopped()`). Its public interface only reads. The coordinator changes it through three role interfaces (`timermodel.h`), which `TimerModel` implements as protected bases: `TimerStateUpdates` (bind the client and clock, show a state, announce connection, context and activity changes, `entryEnded()`, `resetContext()`, `forgetWorkspace()`), `TimerSelectionUpdates` (the next start's choice: `nextStart()`, `startSent()`, `choiceFor()`, `pick()`, `wantLastEntry()`) and `TimerCatalogUpdates` (`readable()`, the `ProjectCatalog` and `NextStartSelection` the reads land in, `showChosenProject()`). `TimerController` hands them over as `TimerModelRoles`; the coordinator keeps all three, and its `ProjectLoader` gets only the catalog role. A panel holding a `TimerModel` cannot reach any of them. There is no friendship. Each update is one operation that sends every notification it causes: `showState()` for each new snapshot, `resetContext()` and `forgetWorkspace()` announce the status, and `connectionReplaced()`, `contextUpdated()` and `activityChanged()` announce what the coordinator changed. The coordinator emits none of the model's signals. The model starts no read: the coordinator's `ProjectLoader` (`projectloader.h`) reads the project list, a chosen project the list lacks and the last entry, and the answers land in the model's `ProjectCatalog` and `NextStartSelection`. The model reads what the actions do through the read-only `TimerActivity` interface, and tells the coordinator of a refused project read with `workspaceRefused()`. The controller forwards its `Q_INVOKABLE` actions and slots to the coordinator, so QML and the tests use one API. Panels read the model and act through the coordinator: the macOS menu and status words take `TimerModel` and `TimerCoordinator`, and `tokkl-timerd` gets both from `main.cpp`. The entry, the pause chain and any Pomodoro session come from the shared `TimerStateClient` (see `map-desktop-timer-state-client-stream-poll-settling-and-revisions`), which QML sets as `stateClient`. The KDE panel, the macOS app and the GNOME `tokkl-timerd` service all use it. It reads time through the `Clock` interface in `desktop/core/src/clock.h`: `SystemClock` in the widget, `FakeClock` from `desktop/core/autotests/fakes.h` in the `timer` test. Keep it that way so the tests can move time.

Elapsed time is recomputed from the entry's server `start` and the client's server time (`TimerStateClient::serverNow()`) on every one-second tick, never counted up locally, so a sleep, a late tick or a skewed clock loses nothing. The controller does not poll. The state client reads the state, follows the event stream and polls every 30 s only while no stream delivers. `resumed()` is the session-wake slot that makes the client read again and replace its stream; it has nothing to do with `resume()` of a pause chain.

`elapsedText` is `formatElapsed(elapsedSeconds)`: whole minutes as truncated `H:MM` (`0:00` under a minute, `125:00` for 125 hours, never rounded up). `formatElapsed` in `desktop/gnome/extension/timer1.js` follows the same rule. A panel test that wants the label to change must advance the clock across a minute boundary (`autotests/qml/tst_panel.qml` does).

Mutation rules:

- Start POSTs `/api/app/timer/start` with the revision shown, the workspace, a UTC RFC 3339 `start` from the clock, the client's `created_with` (`tokkl-kde`, `tokkl-gnome`, `tokkl-macos`), an empty description, and the selected project and billable flag (`encodeTimerStart` in `desktop/core/src/apitypes.cpp`). Stop POSTs `/api/app/timer/stop` with the revision shown. Both go through `TimerStateClient::start()`/`stop()` and `Connection::startTimer()`/`stopTimer()`, answer with the TimerState like the other actions, and answer 409 with the server's state when another device changed the timer first (or, for a stop, when nothing runs), so a desktop start never replaces a start made elsewhere. A server from before those routes answers 404: the write then goes to the v9 route (`POST /workspaces/:wid/time_entries` with `duration: -1`, `PATCH /workspaces/:wid/time_entries/:id/stop`), and so does every later start and stop of that connection generation, as `Connection` does for preferences. When the v9 route answers 404 too, the app route exists and refused the write (a deleted project, say), so nothing is remembered. `POST /api/app/timer/stop` checks only that the running entry's workspace exists, not membership, so a stop no longer reveals a lost workspace; a projects read does.
- `toggle()` pauses a running entry, resumes a paused chain and otherwise starts. It is the primary action on every panel: the KDE panel's click, keys and press action, the macOS status item's click, and the GNOME button's click, Space and Return (through the service's `Pause`, `Resume` and `Start`). Each panel's menu has its own item that calls `start()` or `stop()` and never pauses. It reads Start or Stop on KDE and GNOME, and Start Timer or Stop Timer on macOS. Stop while paused is `POST /api/app/timer/discard` against the revision shown, so it needs `canWrite` like every other action. All actions return false while a session is active.
- One mutation runs at a time; clicks while it runs are ignored.
- What the controller shows comes from one timer state, the one the state client accepted: `TimerView::of` (`desktop/core/src/timerview.h`) derives the entry, chain and session shown, and no reply is patched on top. The billable PUT, and a start or stop that fell back to v9, are v9 calls whose reply is an entry, not the state (`TimerActionResult::entry`). Once one is applied the controller stays busy while the client settles (`TimerStateClient::settle()`), until a read sent after the reply brings the state that shows the change. A read issued before the write cannot end the wait. The billable edit stays a v9 PUT because the server has no revisioned edit of the running entry.
- When the outcome is unknown (network error, timeout, 5xx, unreadable answer), the controller stays busy while the state client settles: until a read sent after the failure brings a state. A start or resume is never sent again, because the server may already have created the entry.
- A connection generation change (another instance, account or credential) drops the answers to requests sent before it. `TimerController::reset` and `PomodoroSession::onGenerationChanged` bump an epoch and clear their pending flags, so the controls work again on the new account and a late answer is ignored.
- A 409 on a timer action (start, stop, pause, resume, discard) adopts the state in the reply and shows "The timer changed on another device first." until the next user action.
- Any other refusal, such as a v9 409 or 404 for an entry that was already stopped, triggers a read of the state. That read clears a stop's error. A refused start or resume keeps its message and the Error status through later reads (`m_keepError`) until the next `setError`, a new mutation, Stop while paused, a project or billable choice, `reconnect()` or a connection reset (`clearKeptError`).

`canWrite` requires the connection to allow writes, a clock, a state client, a state already read (the client's), no lost workspace and no mutation or settling in progress. `canStartNew()` is `canWrite` with nothing running, no chain paused and no session active. `start()` asks it, and so does `PomodoroSession::canStartSession`, which adds only Pomodoro mode and its own pending action, so a 429 cooldown or a lost workspace holds Start session as it holds Start. The session sees the timer only through `TimerActions` (`timeractions.h`), which `TimerCoordinator` implements: `holdsEntry()`, `isBusy()`, `canStartNew()`, the typed `selection()` a session starts with, and `toggle()`. It reads and acts on the server's state through `SessionState` (`sessionstate.h`), which `TimerStateClient` implements; each composition root passes it the timer's own state client, so both read one state. The session sees no `Connection`: it hears of a new account only from `SessionState::accountReset()`. `PomodoroSession::activate()` reports Ignored when `toggle()` sent nothing, as the D-Bus `Activate` contract promises.

Menu actions. `MenuActionStates::of()` (`desktop/core/src/menuactions.h`) decides for every panel which of Start or Stop, Start session, Next phase, End session, Project, Billable and Pomodoro mode show and can be chosen, and each label's key. `MenuActionPolicy` names where the panels differ: `plasma()` and `macos()` wait for `canWrite`, `gnome()` for status Ready (the GNOME menu always read `Status`), and only `plasma()` disables Project and Billable during a session. The KDE menu reads it through `TokklMenuActions`, `StatusMenu` on macOS calls it, and `tokkl-timerd` publishes it as `Actions`. Change a rule there, not in a panel. Do not enable start or stop before that read, or a start could split a timer that already runs on the server. `stale` follows the connection: a transient failure marks the data shown as the last known until it is read again.

A 403 from a workspace operation can mean the account lost the workspace (`memberWorkspace` on the server answers 403 for non-members). The controller then clears the workspace data it exposes, blocks writes and polling, and asks `/me` once whether the account has another workspace. Only a new connection generation or `reconnect()` lifts the block. A start or stop in flight keeps the controller busy through the loss and any reconnect until its reply arrives and a read sent after it reconciles it. A running entry from another workspace is hidden, and starting a new entry stops it on the server, because the API stops the user's running entry in any workspace.

Pause chain. The server owns it (`pause` in the timer state, see `map-timer-state-service-settlement-revision-and-discarded-pomodoro`). `pause()` posts `/api/app/timer/pause`, which stops the running entry and keeps its description, project, task, tags and billable flag with the seconds it stored. `resume()` posts `/api/app/timer/resume` against the revision shown, and the server starts the clone. `elapsedSeconds` is the chain total, the seconds the server stored plus the clone's running time, frozen while paused. A segment paused within half a step of the time resolution rounds to zero and adds nothing (`pauseAndResume` in `desktop/kde/tests/realservertest.cpp` checks this against a real server). A refused resume leaves the chain paused. While paused, `start()`, `chooseProject()` and `chooseBillable()` are refused and the menu reports the chain's project and billable flag. The server ends the chain on a stop of the clone, on any other running entry and on a discard, from any device, and the next state shows it. The widget stores nothing of the chain, so a restart or another device sees the same total. A chain or entry in another workspace is not shown. An unknown outcome of a pause is settled by reads, never by sending the pause again. The API checks a resumed entry's task before its project (`resolveProjectAndTask`), so a chain whose project was deleted gets 404 "Project not found" only when it has no task; with a task it fails on the task. Against a real server, `desktop/kde/tests/realservertest.cpp` covers pause and resume in `pauseAndResume` and the refusal in `resumeRefusedForDeletedProject` (fixture account `a.q`, whose running entry has a project and no task).

The panel menu (`PanelMenu.qml`) drives `chooseProject()` and `chooseBillable()`, and `status` (Unconfigured, Loading, Ready, Busy) summarises the state for the panel. Project sets only the project of the next start and is locked while an entry runs or a chain is paused: the Project submenu and its items are enabled only when `canWrite && !running` (`choosable`), and `chooseProject` returns false and sends nothing while `m_entry` exists or `isPaused()`. To change the project of a running entry, stop it and start a new one. Billable sets the next start and, while an entry runs, edits that entry in place with one PUT (`updateEntry`) that carries only `billable`; the menu shows the new flag once the state read after the reply answers. The server's `updateTimeEntry` keeps whatever the request omits (description, tags, start, stop), so do not add fields the panel did not change. Choosing a project applies its billable default (false for No project) and a later billable choice overrides it. Only an active project of the workspace is a valid choice. Projects load 200 at a time (`projectPageSize`); the project of the running entry is fetched on its own when it is archived, so the menu can name it (checked, disabled) without offering it.

Next-start default. After a stop, the next start uses the stopped entry's project when it is an active project of the workspace, else No project. The project comes from the last state shown before the stop; the revision check means it is the server's. A v9 stop's reply names the project the server stopped, which the model takes instead (`entryEnded()`). A stop answered before the first project list waits for the list (`NextStartDefaults::waitForList`). On connect, and on `reconnect()`, with nothing running the controller reads `GET /me/time_entries?meta=true` (`Connection::fetchRecentEntries`; the API lists only the last 9 days, newest first) and uses the newest entry's project when `project_active` is true; an entry from another workspace gives No project, and after a longer break there is none to use. `reconnect()` refreshes the entry and the projects whenever the connection is up. `NextStartSelection` (`desktop/core/src/nextstartselection.h`) keeps the choice and its defaults, announces it with `changed()` and clears it on `reset()`, which the controller calls for every new generation (another instance, account or secret). `Connection` keeps no choice. `NextStartDefaults` decides when a default may apply. Manual picks and automatic defaults are tracked apart: `NextStartDefaults::picked()` is set by `chooseProject` and `chooseBillable` and is cleared by the next start or stop, a manual pick wins over every automatic default until then, and Reconnect replaces only an automatic default. A billable toggle made before the connect reply arrives also cancels the default.

Panel indicator. `TokklTimer` exposes `indicatorState` and `indicatorColor` with one `indicatorChanged` signal. They follow `chosenProjectId`, which is the running entry's project while an entry runs and the next-start project while stopped. `IndicatorState` is an `enum class` with None (no project, or a 404), Pending (the lookup is running) and Project; a plain `Project` enumerator would hide the `Tokkl::Project` struct. `indicatorColor` is a `QString`, not a `QColor`, so the core needs no Qt Gui: it is lowercase `#rrggbb` in the Project state and empty otherwise, and `ProjectIndicator.qml` tests for the empty string. The input is accepted case-insensitively, the rule of `isHexColor` in `packages/common/colors.ts`. The single-project read (`ProjectLoader::resolveChosenProject()`, then `ProjectCatalog::lookUp` and `Connection::fetchProject`) also resolves a stopped-state project, and runs only for a project outside the active list once that list is known. It runs before `ChosenProject::show()` (`desktop/core/src/chosenproject.h`), so the indicator shows Pending while the read is on its way. The looked-up project is revalidated after every successful projects reload (Reconnect, refresh, resume): `ProjectCatalog::m_lookedUpStale` marks it, and the indicator keeps the old answer until the new read returns, so a rename or recolour shows up without a reconnect. At most one read per project id is in flight (`m_lookupsPending`). Each read records the catalog's `m_listRevision`, and an answer that arrives after a newer list, a 200 or a 404, leaves the project stale and triggers exactly one follow-up read. A 404 is provisional too: `projects.id` is `INTEGER PRIMARY KEY` without `AUTOINCREMENT`, so a deleted top id can be reused by a new project.

`Connection::maxProjectPages` (100) caps paging, so a workspace with more than 20000 projects still loses the rest of its list. It no longer does so silently: the `ProjectList` that `Connection::fetchProjects()` delivers has `incomplete` set when the last page read was full and still brought new projects. `ProjectCatalog` keeps the flag, and `TimerController::projectsIncomplete` (a `Q_PROPERTY` with `NOTIFY projectsChanged`) shows it and clears with the account's data. A page with nothing new ends paging without the flag, since the server then ignored the paging parameters.

Project menu. `ProjectChoices` (`desktop/core/src/projectchoices.h`) is the project submenu every panel builds: No project, then the running or paused entry's project when it is archived (checked, never offered), the note "Project list cut short. Use Open Tokkl for the others." when the list is incomplete, then the active projects, the chosen one checked. A row is offered while `choosable`: `canWrite` with nothing running and no chain paused. `TimerController::projectChoices()` builds it. macOS fills its menu from it. QML reads `projectChoices`, the rows without checked or enabled, so the list changes only with the projects and the held entry's project and an open menu keeps its items while the user picks; `PanelMenu.qml` also locks the menu during a session and gives the note an accessible description. `tokkl-timerd` publishes `Projects` and `ProjectsIncomplete` from it, and the GNOME menu shows the same note before the projects.
