`Tokkl::TimerController` (`desktop/core/src/timercontroller.h`, QML type `TokklTimer`) is the timer as one object, in two halves. `TimerModel` (`timermodel.h`), which the controller is, holds what a panel shows: the view of the accepted state, elapsed time, the projects (`ProjectCatalog`, `ChosenProject`), the next-start choice (`NextStartSelection`), the status and canWrite, with read-only accessors and every view signal. `TimerCoordinator` (`timercoordinator.h`), which the controller owns, holds the actions and what keeps them safe: the state client and connection it binds, the epoch, the `MutationGate` and its messages, and the lost-workspace block and rediscovery. It reports the end of each write in `writeFinished(ok, message)`, with the words `errorString()` shows; a new generation ends a write still on its way with an empty message. The model owns the project catalog and the next-start selection and applies the next-start defaults (the stop reply from `entryEnded()`, `NextStartSelection::stopped()`). Its public interface only reads. The coordinator changes it through three role interfaces (`timermodel.h`), which `TimerModel` implements as protected bases: `TimerStateUpdates` (bind the client and clock, show a state, announce connection, context and activity changes, `entryEnded()`, `resetContext()`, `forgetWorkspace()`), `TimerSelectionUpdates` (the next start's choice: `nextStart()`, `startSent()`, `choiceFor()`, `pick()`, `wantLastEntry()`) and `TimerCatalogUpdates` (`readable()`, the narrow reads `readProjects()`, `lookUpProject()`, `takeLastEntryWanted()`, `readLastEntry()` and `onProjectsAnswered()`, and `showChosenProject()`; it never hands out the model's `ProjectCatalog` or `NextStartSelection`). `TimerController` hands them over as `TimerModelRoles`; the coordinator keeps all three, and its `ProjectLoader` gets only the catalog role. A panel holding a `TimerModel` cannot reach any of them. There is no friendship. Each update is one operation that sends every notification it causes: `showState()` for each new snapshot, `resetContext()` and `forgetWorkspace()` announce the status, and `connectionReplaced()`, `contextUpdated()` and `activityChanged()` announce what the coordinator changed. The coordinator emits none of the model's signals. The model starts no read: the coordinator's `ProjectLoader` (`projectloader.h`) reads the project list, a chosen project the list lacks and the last entry, and the answers land in the model's `ProjectCatalog` and `NextStartSelection`. The model reads what the actions do through the read-only `TimerActivity` interface, and tells the coordinator of a refused project read with `workspaceRefused()`. The controller forwards its `Q_INVOKABLE` actions and slots to the coordinator, so QML and the tests use one API. The menus read the choice as `chosenProjectId` and `chosenBillable`, which only read; there is no separate next-start property. It changes through `chooseProject()` and `chooseBillable()`, which ask `TimerModel::canChooseProject()` and `canChooseBillable()`, and nothing else writes it. Panels read the model and act through the coordinator: the macOS menu and status words take `TimerModel` and `TimerCoordinator`, and `tokkl-timerd` gets both from `main.cpp`. The entry, the pause chain and any Pomodoro session come from the shared `TimerStateClient` (see `map-desktop-timer-state-client-stream-poll-settling-and-revisions`), which QML sets as `stateClient`. The KDE panel, the macOS app and the GNOME `tokkl-timerd` service all use it. It reads time through the `Clock` interface in `desktop/core/src/clock.h`: `SystemClock` in the widget, `FakeClock` from `desktop/core/autotests/fakes.h` in the `timer` test. Keep it that way so the tests can move time.

Elapsed time is recomputed from the entry's server `start` and the client's server time (`TimerStateClient::serverNow()`) on every one-second tick, never counted up locally, so a sleep, a late tick or a skewed clock loses nothing. The controller does not poll. The state client reads the state, follows the event stream and polls every 30 s only while no stream delivers. `resumed()` is the session-wake slot that makes the client read again and replace its stream; it has nothing to do with `resume()` of a pause chain.

`elapsedText` is `formatElapsed(elapsedSeconds)`: whole minutes as truncated `H:MM` (`0:00` under a minute, `125:00` for 125 hours, never rounded up). `formatElapsed` in `desktop/gnome/extension/timer1.js` follows the same rule. A panel test that wants the label to change must advance the clock across a minute boundary (`autotests/qml/tst_panel.qml` does).

Mutation rules:

- `GET /api/app/status` (not the Toggl `/me` body) carries `api_version` and `capabilities`, decoded by `serverApiFromResponse()` into a `ServerApi`. `ServerFloor` in `desktop/core/src/apitypes.h` is the one place that names the oldest server the desktop apps support: `api_version` 1 with `app-preferences`, `timer-actions`, `pause-revision`, `pomodoro-revision`, `timer-edit-entry`, `idempotency-keys`, `catalog-revision` and `latest-entry` (the first server release after 2.1.0). Every fake transport and fixture that answers `/api/app/status` announces the whole floor: `currentServerApi()` in `desktop/core/autotests/fakes.h`, the status in `kde/autotests/kdeconnectiontest.cpp` and the rows in `core/autotests/apitest.cpp`. `FakeTransport` answers the catalog revision from the event loop like the status (`catalog`, `holdCatalog`, `respondCatalog()`, `catalogAt()`), so a list read follows one event-loop turn after the read that asked; a test that changes the projects sets a new revision first. `AuthSession` reads the status before a generation's first `/me` and binds the account only when `ServerApi::isSupported()`; an older server, an answer without the fields or a 4xx still gets `/me` (so a wrong address or refused credentials say so), then the state is `Error` with "This Tokkl server is too old for this app; update the server." Every panel shows it through the usual Error status and detail. A status read with no answer, a timeout, a 5xx or a 429 fails the validation the way the same `/me` failure would, without sending `/me`. An unsupported announcement is asked for again by the next validation (the retry timer, a revalidation, a reconnect); a supported one holds for the generation. `decodeMe()` ignores the fields. There are no v9 write fallbacks: every write goes to `/api/app`, and a 404 is a refusal like any other.
- Start POSTs `/api/app/timer/start` with the revision shown, the workspace, a UTC RFC 3339 `start` from the clock, the client's `created_with` (`tokkl-kde`, `tokkl-gnome`, `tokkl-macos`), an empty description, and the selected project and billable flag (`encodeTimerStart` in `desktop/core/src/apitypes.cpp`). Stop POSTs `/api/app/timer/stop` with the revision shown. Both go through `TimerStateClient::start()`/`stop()` and `Connection::startTimer()`/`stopTimer()`, answer with the TimerState like the other actions, and answer 409 with the server's state when another device changed the timer first (or, for a stop, when nothing runs), so a desktop start never replaces a start made elsewhere. `POST /api/app/timer/stop` checks only that the running entry's workspace exists, not membership, so a stop no longer reveals a lost workspace; a projects read does.
- `toggle()` pauses a running entry, resumes a paused chain and otherwise starts, as `TimerModel::toggleAction()` says. `PomodoroSession::primaryAction()` is what a panel's click does (`PrimaryAction` in `timeractions.h`), `activate()` acts on it, and the panels name the click from its key (`primaryActionKey()`, `TokklStatusParts.action`). It is the primary action on every panel: the KDE panel's click, keys and press action, the macOS status item's click, and the GNOME button's click, Space and Return (through the service's `Pause`, `Resume` and `Start`). Each panel's menu has its own item that calls `start()` or `stop()` and never pauses. It reads Start or Stop on KDE and GNOME, and Start Timer or Stop Timer on macOS. Stop while paused is `POST /api/app/timer/discard` against the revision shown, so it needs `canWrite` like every other action. All actions return false while a session is active.
- One mutation runs at a time; clicks while it runs are ignored.
- What the controller shows comes from one timer state, the one the state client accepted: `TimerView::of` (`desktop/core/src/timerview.h`) derives the entry, chain and session shown, and no reply is patched on top. The billable edit is `POST /api/app/timer/edit` with the running entry's `entry_id` and no revision, through `TimerStateClient::edit()`, and the state it answers with shows the change. A change elsewhere that leaves that entry running does not refuse it; the server answers 409 only once the entry stopped, and that shows as a conflict.
- Start and Pomodoro start carry an `Idempotency-Key`, a new one per click (`ApiClient::newIdempotencyKey()`, sent by `Connection::startTimer()` and `startPomodoro()` through `ApiClient::keyedAction()`). When the outcome is unknown the same body and key go out once more after one retry wait, `retryWaitMs(retryMinMs)` in `clock.h` (1 s plus up to a quarter more at random, the rule the state client's reconnect backoff uses too), because a send at once would likely meet the same failure; a server that acted on the first answers with what it did then. The wait runs on a `QTimer` owned by the `ApiClient` and checks the generation, so a new generation or the client's end drops it and `done` never runs. A refusal, a 409 or a session that refuses the second send (a cooldown) ends it with the first answer.
- When the outcome is unknown (network error, timeout, 5xx, unreadable answer), and for a start also after that second send, the controller stays busy while the state client settles: until a read sent after the failure brings a state. Nothing else is sent again; a resume has no key and the server may already have created the clone.
- A connection generation change (another instance, account or credential) drops the answers to requests sent before it. `TimerController::reset` and `PomodoroSession::onGenerationChanged` bump an epoch and clear their pending flags, so the controls work again on the new account and a late answer is ignored.
- A 409 on a timer action (start, stop, pause, resume, discard) adopts the state in the reply and shows "The timer changed on another device first." until the next user action.
- Any other refusal, such as a 404 for a workspace or project that is gone, triggers a read of the state. That read clears a stop's error. A refused start or resume keeps its message and the Error status through later reads (`m_keepError`) until the next `setError`, a new mutation, Stop while paused, a project or billable choice, `reconnect()` or a connection reset (`clearKeptError`).

`canWrite` requires the connection to allow writes, a clock, a state client, a state already read (the client's), no lost workspace and no mutation or settling in progress. `canStartNew()` is `canWrite` with nothing running, no chain paused and no session active. `start()` asks it, and so does `PomodoroSession::canStartSession`, which adds only Pomodoro mode and its own pending action, so a 429 cooldown or a lost workspace holds Start session as it holds Start. The session sees the timer only through `TimerActions` (`timeractions.h`), which `TimerCoordinator` implements: `holdsEntry()`, `isBusy()`, `canStartNew()`, the typed `selection()` a session starts with, and `toggle()`. It reads and acts on the server's state through `SessionState` (`sessionstate.h`), which `TimerStateClient` implements; each composition root passes it the timer's own state client, so both read one state. The session sees no `Connection`: it hears of a new account only from `SessionState::accountReset()`. `PomodoroSession::activate()` reports Ignored when `toggle()` sent nothing, as the D-Bus `Activate` contract promises.

Menu actions. `MenuActionStates::of()` (`desktop/core/src/menuactions.h`) decides for every panel which of Start or Stop, Start session, Next phase, End session, Project, Billable and Pomodoro mode show and can be chosen, and each label's key. Project and Billable follow `TimerModel::canChooseProject()` and `canChooseBillable()`, the rule the coordinator enforces: both are locked during a Pomodoro session, whose open pomodoro is a running entry, on every panel. `MenuActionPolicy` keeps only GNOME's extra wait for status Ready (the GNOME menu always read `Status`); a policy can grey out more but never allow what the timer refuses. `plasma()` and `macos()` add nothing. The KDE menu reads it through `TokklMenuActions`, `StatusMenu` on macOS calls it, and `tokkl-timerd` publishes it as `Actions`. Change a rule there, not in a panel. Do not enable start or stop before that read, or a start could split a timer that already runs on the server. `stale` follows the connection: a transient failure marks the data shown as the last known until it is read again.

A 403 from a workspace operation can mean the account lost the workspace (`memberWorkspace` on the server answers 403 for non-members). The controller then clears the workspace data it exposes, blocks writes and polling, and asks `/me` once whether the account has another workspace. Only a new connection generation or `reconnect()` lifts the block. A start or stop in flight keeps the controller busy through the loss and any reconnect until its reply arrives and a read sent after it reconciles it. A running entry from another workspace is hidden, and starting a new entry stops it on the server, because the API stops the user's running entry in any workspace.

Pause chain. The server owns it (`pause` in the timer state, see `map-timer-state-service-settlement-revision-and-discarded-pomodoro`). `pause()` posts `/api/app/timer/pause` against the revision shown, which stops the running entry and keeps its description, project, task, tags and billable flag with the seconds it stored. `resume()` posts `/api/app/timer/resume` against the revision shown, and the server starts the clone. `elapsedSeconds` is the chain total, the seconds the server stored plus the clone's running time, frozen while paused. A segment paused within half a step of the time resolution rounds to zero and adds nothing (`pauseAndResume` in `desktop/kde/tests/realservertest.cpp` checks this against a real server). A refused resume leaves the chain paused. While paused, `start()`, `chooseProject()` and `chooseBillable()` are refused and the menu reports the chain's project and billable flag. The server ends the chain on a stop of the clone, on any other running entry and on a discard, from any device, and the next state shows it. The widget stores nothing of the chain, so a restart or another device sees the same total. A chain or entry in another workspace is not shown. An unknown outcome of a pause is settled by reads, never by sending the pause again. The API checks a resumed entry's task before its project (`resolveProjectAndTask`), so a chain whose project was deleted gets 404 "Project not found" only when it has no task; with a task it fails on the task. Against a real server, `desktop/kde/tests/realservertest.cpp` covers pause and resume in `pauseAndResume` and the refusal in `resumeRefusedForDeletedProject` (fixture account `a.q`, whose running entry has a project and no task).

The panel menu (`PanelMenu.qml`) drives `chooseProject()` and `chooseBillable()`, and `status` (Unconfigured, Loading, Ready, Busy) summarises the state for the panel. Project sets only the project of the next start and is locked while an entry runs, a chain is paused or a Pomodoro session is active: `TimerModel::canChooseProject()` is the rule, the Project submenu and its items are enabled only when it allows (`choosable`), and `chooseProject` returns false and sends nothing otherwise. Billable is locked while paused or during a session (`canChooseBillable()`). To change the project of a running entry, stop it and start a new one. Billable sets the next start and, while an entry runs, edits that entry in place with one write (`updateEntry`) that carries only `billable`: the timer edit against the revision shown. The server keeps whatever the request omits (description, tags, start, stop), so do not add fields the panel did not change. Choosing a project applies its billable default (false for No project) and a later billable choice overrides it. Only an active project of the workspace is a valid choice. Projects load 200 at a time (`projectPageSize`); the project of the running entry is fetched on its own when it is archived, so the menu can name it (checked, disabled) without offering it.

Next-start default. After a stop, the next start uses the stopped entry's project when it is an active project of the workspace, else No project. The project comes from the last state shown before the stop; the revision check means it is the server's. A stop answered before the first project list waits for the list (`NextStartDefaults::waitForList`). On connect, and on `reconnect()`, with nothing running the controller reads `GET /api/app/time_entries/latest` (`Connection::fetchLatestEntry()`, capability `latest-entry`): the account's newest entry by start in any workspace, running or stopped, with the `meta=true` fields, or `null`. It is the first entry `/me/time_entries?meta=true` would list, so the default is the one the old list read gave, without its nine-day limit or its size. `NextStartSelection::fromLatestEntry()` uses its project when `project_active` is true and the entry is in the bound workspace; an archived or deleted project, an entry from another workspace, an entry without a project and `null` give No project. `reconnect()` refreshes the entry and checks the project list whenever the connection is up. `NextStartSelection` (`desktop/core/src/nextstartselection.h`) keeps the choice and its defaults, announces it with `changed()` and clears it on `reset()`, which the controller calls for every new generation (another instance, account or secret). `Connection` keeps no choice. `NextStartDefaults` decides when a default may apply. Manual picks and automatic defaults are tracked apart: `NextStartDefaults::picked()` is set by `chooseProject` and `chooseBillable` and is cleared by the next start or stop, a manual pick wins over every automatic default until then, and Reconnect replaces only an automatic default. A billable toggle made before the connect reply arrives also cancels the default.

Panel indicator. `TokklTimer` exposes `indicatorState` and `indicatorColor` with one `indicatorChanged` signal. They follow `chosenProjectId`, which is the running entry's project while an entry runs and the next-start project while stopped. `IndicatorState` is an `enum class` with None (no project, or a 404), Pending (the lookup is running) and Project; a plain `Project` enumerator would hide the `Tokkl::Project` struct. `indicatorColor` is a `QString`, not a `QColor`, so the core needs no Qt Gui: it is lowercase `#rrggbb` in the Project state and empty otherwise, and `ProjectIndicator.qml` tests for the empty string. The input is accepted case-insensitively, the rule of `isHexColor` in `packages/common/colors.ts`. The single-project read (`ProjectLoader::resolveChosenProject()`, then `ProjectCatalog::lookUp` and `Connection::fetchProject`) also resolves a stopped-state project, and runs only for a project outside the active list once that list is known. It runs before `ChosenProject::show()` (`desktop/core/src/chosenproject.h`), so the indicator shows Pending while the read is on its way. The looked-up project is revalidated after every successful projects reload (Reconnect, refresh, resume): `ProjectCatalog::m_lookedUpStale` marks it, and the indicator keeps the old answer until the new read returns, so a rename or recolour shows up without a reconnect. At most one read per project id is in flight (`m_lookupsPending`). Each read records the catalog's `m_listsRead`, and an answer that arrives after a newer list, a 200 or a 404, leaves the project stale and triggers exactly one follow-up read. A 404 is provisional too: `projects.id` is `INTEGER PRIMARY KEY` without `AUTOINCREMENT`, so a deleted top id can be reused by a new project.

Project reads. Every read of the list starts with `GET /api/app/workspaces/{wid}/catalog` (`Connection::fetchCatalogRevision()`, capability `catalog-revision`), whose `revision` the server bumps with every write that changes what the v9 list answers: project create, update, archive and delete, client rename, archive and delete, imports and a default-currency change (see `map-catalog-revision-and-latest-entry-endpoints`). `ProjectCatalog::fetch()` keeps the list when the revision equals the one the list was read at, and otherwise pages in the whole active list (`Connection::fetchProjects()`). It keeps the revision read before that list, so a write that lands while the list is on its way shows on the next refresh. A new generation, a lost workspace (`forget()`) and a failed read leave no revision, so the next read is a whole one. A cut-short list is kept like any other while the revision holds, because the same revision gives the same pages. A 403 on the revision read is a workspace refusal like any other read's. One read (revision and list) is in flight at a time; a refresh meanwhile sends nothing. A refresh, a wake, a return from a connectivity failure and Reconnect all go through the same check. There is no `since` delta read and no timed whole read any more: they missed client renames and kept deleted projects.

`Connection::maxProjectPages` (100) caps paging, so a workspace with more than 20000 projects still loses the rest of its list. It no longer does so silently: the `ProjectList` that `Connection::fetchProjects()` delivers has `incomplete` set when the last page read was full and still brought new projects. `ProjectCatalog` keeps the flag, and `TimerController::projectsIncomplete` (a `Q_PROPERTY` with `NOTIFY projectsChanged`) shows it and clears with the account's data. A page with nothing new ends paging without the flag, since the server then ignored the paging parameters.

Project menu. `ProjectChoices` (`desktop/core/src/projectchoices.h`) is the project submenu every panel builds: No project, then the running or paused entry's project when it is archived (checked, never offered), the note "Project list cut short. Use Open Tokkl for the others." when the list is incomplete, then the active projects, the chosen one checked. A row is offered while `choosable`: `TimerModel::canChooseProject()`, so `canWrite` with nothing running, no chain paused and no session active. `TimerController::projectChoices()` builds it. macOS fills its menu from it. QML reads `projectChoices`, the rows without checked or enabled, so the list changes only with the projects and the held entry's project and an open menu keeps its items while the user picks; `PanelMenu.qml` also locks the menu during a session and gives the note an accessible description. `tokkl-timerd` publishes `Projects` and `ProjectsIncomplete` from it, and the GNOME menu shows the same note before the projects.
