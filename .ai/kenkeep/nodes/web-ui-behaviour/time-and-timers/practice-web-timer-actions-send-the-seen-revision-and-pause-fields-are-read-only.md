Start, Stop, Pause, Resume, Stop while paused and the Pomodoro actions are timer actions (`packages/web/src/api/timerHooks.ts`). Start (`useStartTimer`, `POST /api/app/timer/start`), Stop (`useStopTimer`, `POST /api/app/timer/stop`), Pause (`pauseTimer`, `POST /api/app/timer/pause`, `pause-revision`), resume, discard (Stop while paused), Pomodoro start (`startPomodoro`, `POST /api/app/pomodoro`), Next phase and End session send the revision of the cached state. Every reply, and the body of a 409, goes through `acceptTimerState`, so the views show the server's state with no local guess. Do not add client-side chain or session bookkeeping; the pieces that were once kept per account in `localStorage` are gone.

An edit of the running entry, such as the description saved as the user clicks Next phase, moves the revision. `currentRevision` first waits for pending writes that can move the revision (`settleOtherWrites`) and reads the state again. `revisionToSend` then uses the fresh revision only if the session phase and the pause are the ones the user saw. Otherwise it sends the seen revision and lets the server answer with a conflict. Only mutations with `meta: MOVES_TIMER` (`api/timerState.ts`) count: every entry hook in `api/entries.ts`, and `useAction` calls passing `movesTimer: true` for edits of what the running entry shows (project, client, task and tag edits and deletes) and for imports. A new write that can change the running entry, its project, client, task or tags, or the session or pause must carry the mark. Preference, profile, password, workspace and admin saves carry none, so they never delay Resume or End session. Timer actions are unmarked, so an action never waits for itself. A marked write that TanStack holds for the connection (`isPaused`), such as an entry edit made offline, fails the wait at once with the `offline` error, so the action never goes out late after reconnect; an unmarked held write does not.

Failures become `TimerActionError` (`api/timerState.ts`): kind `conflict` for a 409 whose body is a timer state ("Another device changed the timer first."), and `offline` when fetch rejects or the request runs past its deadline (`RequestTimeoutError` from `api/client.ts`). Mutations use `networkMode: 'always'`, so an offline action fails at once instead of waiting and firing late. Start sends the draft's fields and an explicit `start` (the bar's `markOwnStart` second), and Continue and favorites use the same call, because the server stops a running entry at the new start. Stop sends an explicit `stop` from the server-corrected clock (`serverNow`). The reply is a timer state, not the stopped entry, so `useTimerBarActions` tells that the entry went to the trash ("Too short to keep") from `snappedSeconds(current.start, stop)` being 0: the revision vouches for the start it showed, and `snappedSeconds` snaps as the server does. Because both carry a revision, a Start or Stop after a write whose outcome is unknown is refused with a 409 and the server's state if that write landed. The finished entry typed into the idle bar as a duration is still a v9 create, through `useAddTypedEntry` (`api/entries.ts`), with `networkMode: 'always'` and `attemptTimerRequest` (`api/timerHooks.ts`), which turns a TypeError into the `offline` error. Other creates (calendar, manual form, editor, duplicate) keep `useCreateEntry` and the default network mode.

Edits of the running entry from the timer bar and the Pomodoro page (`useUpdateRunningEntry` and `updateRunningEntry` in `api/entries.ts`) post to `POST /api/app/timer/edit` through `editRunningEntry` (`api/timerHooks.ts`) with the cached revision, and the reply is a timer state that goes through `acceptTimerState`. They can change only the description, project, task, billable and tags (`RunningEntryChanges`); tags sent replace the entry's tags and a null project or task clears it. They keep the entry's mutation scope (`entryScope`), so they stay in order with other edits of that entry, and each one reads the cached revision when its turn comes, after the edit before it moved it. They carry `MOVES_TIMER` but do not call `settleOtherWrites`, which would wait for the edit itself. A 409 with a state is adopted. An edit only sets fields, so when that state still runs the entry the edit was made for, only the revision moved and the same edit goes out once more at the new revision, keeping what the user typed; when it runs another entry or none, or the retry conflicts too, the edit fails with the `conflict` error and is never applied to another entry. A request with no reply keeps its own error (not the `offline` one), as a stopped-entry edit does. Edits of stopped entries stay on the v9 PUT (`updateEntry`), and so does the entry editor's save of the running entry, because it can move the start, which the timer edit route never changes.

Every write that starts, stops or changes what the timer shows goes through `timerWrite` (`api/timerHooks.ts`): the timer actions (inside `attemptTimerRequest`), the typed duration, running-entry edits and Discard (`useDiscardRunningEntry`). A failure counts as an unknown outcome (`isOutcomeUnknown` in `api/timerState.ts`) when fetch rejects, the deadline passes, the server answers 5xx, or a 2xx reply does not parse (`UnparsableReplyError` from `api/client.ts`) or decode (`DecodeError`, `UnreadableTimerStateError`). The error keeps its message, and the QueryClient is marked. The next timer write first reads `GET /api/app/timer` (`reconcileTimer`). If the read revision differs from the cached one, the lost write may have landed: the state is adopted and the write fails with the `conflict` error without being sent. If the read fails, nothing is sent and the mark stays. The v9 writes carry no revision, so this read is what keeps a retried Discard from applying on top of a landed one. It cannot catch a duplicate finished entry, because a finished create does not move the revision; the typed entry relies on its `Idempotency-Key` instead (see below). A 4xx is a refusal and marks nothing.

Every create the server keys carries an `Idempotency-Key` header: v9 creates of entries, clients, projects, tasks and tags, the entry split, timer start and Pomodoro start. They go through `postCreate` or `sendCreate` in `api/idempotency.ts`; a new create the server keys must too. One key stands for one user intent. A create whose outcome is unknown (`isOutcomeUnknown`) goes out once more at once with the same body and key, inside the same `timerWrite` for the timer starts and the typed entry, so only a second unknown outcome marks the timer. After that, the key stays kept for that exact request (method, path and JSON body) for 23 hours, under the server's 24, so the same request sent again, such as Save clicked again on the form the error left open, is answered with the record the lost one made. Any reply, a refusal included, settles the intent, and an identical create after it gets a new key, so adding the same duration twice on purpose stores two entries. Keys are 32 hex characters from `crypto.getRandomValues`; `crypto.randomUUID` needs a secure context, and an instance may be served over plain HTTP. Do not go back to guessing whether a lost create landed by diffing lists. `api/idempotency.test.ts` covers the key reuse. `api/timerHooks.test.ts` covers the Start and Stop requests, the adopted conflict state and the reconciling read.

In the timer bar (`timerBarView` in `timerBarView.ts`, read by `TimerBar.tsx`), `paused` means a state with `pause.paused` and no running entry. The bar then shows the chain's fields (`pauseDraft` in `pauseView.ts`) in read-only inputs, because Resume starts a clone of what the server holds. The clock is `barSeconds`: the chain's `seconds` plus the clone's elapsed time while it runs, frozen while paused. Plain Stop on a running entry is the timer stop; the server ends the chain when the stopped entry is its clone. Chain and session rules live in the server (see `map-timer-state-service-settlement-revision-and-discarded-pomodoro`). Pausing is refused during a session.
