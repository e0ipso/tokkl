- Every request in `packages/web/src/api/client.ts` runs under a deadline that covers the reply body too (`withDeadline`, built on `AbortSignal.timeout` and `AbortSignal.any`). `DEADLINE_MS` holds three kinds: `read` 20 s, `write` 30 s, `transfer` 5 min. `requestKind` picks one from the method and body: a GET is a read, a `RawBody` (CSV or JSON import) a transfer, anything else a write. A caller can name the kind; the report queries in `api/reports.ts` are POSTs and pass `kind: 'read'`. Running out of time fails with `RequestTimeoutError` and the `api.timedOut` message.
- `download` (the JSON and CSV exports, both GETs, and the CSV report POSTs) has a deadline only for its reply to start (`DOWNLOAD_START_MS`, the 5 min transfer deadline); the body is then read with `response.blob()` for as long as it takes. The server streams exports at the pace the client reads and drops a client that stops reading, which fails the download as a network error, so a fixed total deadline only failed large exports on slow links. Reading a chunked body piece by piece with `getReader()` made Chromium report the finished request as `net::ERR_ABORTED`, which the e2e runtime guard fails on, so the body is not read that way. Exports stay on fetch rather than a browser-followed `a[href]` download, although a GET needs no CSRF header and the cookie would go along. A followed link would lose the toasts users see today for a refusal before the first byte (403 for a lost session, 503 `Download took too long` from a full download lane), and `ExportData` could not tell when the file is done to re-enable its buttons. The cost: the whole file is held in memory as a Blob before it is saved. `fetchDownload` and `download` take a `signal` that cancels the request and the body read, failing with the signal's reason (never `RequestTimeoutError`); a cancelled `download` saves nothing. `ExportData` and the reports `ExportButtons` take each download's signal from `useCancellable` (`components/useUnmountSignal.ts`), which aborts on the Cancel button the group shows while a download runs (accessible name "Cancel download", visible text "Cancel") or when the page unmounts (`useUnmountSignal`), and `reportUnlessCancelled` keeps either cancel out of the error toast. After a Cancel, focus returns to the export button that started the download, because the Cancel button goes away. E2e specs pick export buttons by name inside the group (`CSV (detailed)`, `Export JSON`), which "Cancel download" never matches. The CSV report POST only reads, so cancelling it leaves nothing half done, and the e2e runtime guard lets an aborted POST under `/api/app/report` pass like an aborted GET.
- Read query functions forward TanStack's `signal` (`queryFn: ({ signal }) => api.get(path, { signal, … })`), so a read that a refetch replaces or that no view observes any more is aborted. A cancel keeps its `AbortError`, so TanStack still treats the query as cancelled, not failed. The report queries (`reportOptions`, `detailedEntriesOptions` and `weeklyReportOptions` in `api/reports.ts`) are POSTs sent with `kind: 'read'` and forward it too: the server frees a cancelled report's place in the account's report queue, so a report the filters replaced no longer pushes the newest one into a 503. `api/reports.test.ts` checks that each one aborts when its view moves to other filters. Do not forward the signal to any other POST: a cancelled write may still have landed, and the e2e guard fails on an aborted POST outside `/api/app/report`.
- A timer write that times out is treated as one that got no reply: `explainTimerActionError` turns `RequestTimeoutError` into the `offline` `TimerActionError`. It, a 5xx and a 2xx reply that does not parse or decode leave the outcome unknown, and the next timer write reads the timer state first (`timerWrite`, see `practice-web-timer-actions-send-the-seen-revision-and-pause-fields-are-read-only`). `request` throws `UnparsableReplyError` (a `SyntaxError` with the parser's message) for a 2xx body that is not JSON.
- Preference saves (`savePreferencesOptions` in `api/account.ts`) share the mutation scope `preferences`, so TanStack sends them one at a time in the order made; a queued one is `isPaused` until the one before it settles. `createPreferenceSaves` (`api/preferenceSaves.ts`, one per QueryClient) keeps the cache at the latest server reply with the changes of the saves still waiting on top. A failed save drops only its own changes, so it can neither undo an earlier save that succeeded nor wipe a later change. Do not go back to snapshotting the whole object in `onMutate` and restoring it in `onError`. `api/account.test.ts` covers the interleavings.
- Edits of one entry share the mutation scope `entry:<id>` (`entryScope` and `updateEntry` in `api/entries.ts`), so two quick edits of the running entry (`updateRunningEntry`, posted to `/api/app/timer/edit`), such as a description saved on blur and a project picked right after, go out in the order made, and a save of that entry from the entry editor, which goes the same way, queues with them. A scope is fixed per TanStack mutation, so `useUpdateEntry` and `useUpdateRunningEntry` build one mutation per edit (`MutationCache.build`, in `inEntryScope`) and return `mutate`/`mutateAsync` only; there is no `isPending`. A queued edit is `isPaused`, so `settleOtherWrites` (`api/timerState.ts`) fails a timer action as offline only for a paused write that is held for the connection (`isHeldForConnection`), and waits for one queued in its scope. `api/entries.test.ts` covers both.
